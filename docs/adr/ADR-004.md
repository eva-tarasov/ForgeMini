# ADR-004 — Setup-фаза: зависимости ставятся с сетью, агент и Verifier работают без неё

**Статус:** принято, реализовано (этап D.0, 2026-11-23).

## Проблема
Агент и Verifier работают в контейнере с `--network none`, и это одно из главных обещаний продукта. Но из-за этого
у настоящего проекта нет его зависимостей: `import requests` падает и до правки, и после. Verifier в таком случае
никогда не скажет PASS: тесты красные в обоих прогонах. До сих пор обходной путь был один — собрать свой образ и передать
его через `--image`. Для демо это годится, для чужого репозитория — нет.

## Решение
Отдельная фаза **до** песочницы, включается явно: `forge solve --setup "pip install -r requirements.txt"`.

1. Контейнер из базового образа, **с сетью** (обычный bridge), в `/workspace` — снимок исходников.
2. Выполняется команда установки (тайм-аут 600 с). Ненулевой код или тайм-аут — `SetupError`: ран завершается с
   `failure_code = setup_failed` и хвостом вывода установки, агент не запускается.
3. `/workspace` очищается, контейнер фиксируется `docker commit` в образ `forgemini-env:<хеш>`.
4. Агент и оба прогона Verifier стартуют из этого образа **без сети**, как и раньше. В evidence записывается
   производный образ.

Тег — `sha256(id базового образа, команда setup, sha256 снимка исходников)`. Verifier запрашивает тот же тег и обычно
получает тот же образ, что был у агента, без повторной установки.

## Почему так
- **Почему не дать сеть агенту.** Тогда модель может скачать что угодно, а тест может зависеть от внешнего мира.
  Результат перестаёт быть воспроизводимым, и «проверено» теряет смысл. Сеть нужна установке, а не решению задачи.
- **Почему `docker commit`, а не volume с site-packages.** Volume пришлось бы подключать в каждый контейнер, и он живёт
  отдельно от образа: его можно случайно переиспользовать для другого проекта. Образ неизменяем и адресуется
  содержимым: один хеш — одно окружение.
- **Почему `/workspace` очищается перед commit.** Каждый контейнер загружает ровно тот снимок, который должен проверить.
  Если бы образ нёс копию исходников или артефакты сборки (`*.egg-info`, `build/`), они появились бы в снимке контейнера
  и попали в changeset как «правки агента». Тест `test_derived_image_has_an_empty_workspace_so_the_changeset_stays_exact`
  ломается, если убрать очистку (проверено).
- **Почему тег включает снимок исходников.** `requirements.txt` — часть исходников. Изменился файл — нужна новая
  установка. Цена: любая правка исходников даёт новую установку. Для прототипа это приемлемо; точнее было бы хешировать
  только файлы зависимостей, но какие файлы читает произвольная команда, заранее не известно.

## Риски и что с ними сделано
- **Команда установки — это код репозитория с доступом в сеть.** `pip install` исполняет `setup.py` и build-бэкенды.
  Поэтому фаза **opt-in**, а подсказка `--setup` прямо говорит: «только для кода, которому доверяете». Ограничения те же,
  что у песочницы: `--cap-drop ALL`, `no-new-privileges`, лимиты памяти/CPU/процессов, без монтирования папок хоста,
  без секретов в окружении (ключ OpenAI живёт в процессе сервера, в контейнер не передаётся).
- **Из bridge-сети виден хост.** Сервисы, которые слушают на всех интерфейсах (или `host.docker.internal` в Docker
  Desktop), доступны установке. Не закрыто: для локального однопользовательского прототипа принято осознанно.
- **Невоспроизводимость установки.** `pip install` без закреплённых версий может поставить разное в разные дни. Если
  образ удалили между раном и проверкой, Verifier соберёт его заново и может получить другие версии. Evidence фиксирует
  тег образа; закреплять версии — ответственность проекта (lock-файл).
- **Место на диске.** Каждая уникальная комбинация оставляет образ. Убрать все: `docker image prune -a --filter label=forge.env=1`.

## Не входит
Кэш скачанных пакетов между разными установками, установка системных пакетов (`apt-get`, скорее всего, не сработает при `--cap-drop ALL`; не проверялось),
языки кроме Python не проверялись.
