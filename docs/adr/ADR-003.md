# ADR-003 — Чистка унаследованного кода M1

**Статус:** **выполнено** (C1–C5, PR #9–#16, 2026-11-22). Итог — раздел «Итог» ниже; остальной текст — запись плана и измерений до чистки.
**Дата измерения:** 2026-11-22, база `2dda79a`. Воспроизвести: `python3 scripts/inventory/import_graph.py` (`--why МОДУЛЬ`, `--tests`).

> ## Поправка (2026-11-22): первая версия этого ADR завышала «удаляется без рефакторинга»
> Первая версия говорила: «2 173 строки (24 модуля) недостижимы и удаляются сразу». Это неверно, и вот почему.
> 1. **«Недостижимо из ядра» ≠ «не используется».** `app.main` регистрирует все роутеры. Девять из 24 модулей (784 строки) — это
>    живое публичное API `approvals`/`evidence`, их держит только `main`. Реально мертвы в проде **15 модулей / 1 389 строк**.
> 2. **Мёртвый в проде ≠ можно удалять.** Я попробовал удалить эти 15 модулей: **ломаются 39 тестовых файлов**, и ни один не
>    импортирует *только* мёртвое. Мёртвые классы служат **подставками (fixtures) в тестах живых вещей**: `approved_tool_executor`
>    держат 4 теста живого API approvals, `langgraph_runner` (19 строк) — 5 ядровых тестов `AgentService`
>    (в т.ч. `test_agent_service_integration`, 2 260 строк), `verification_service` — 4 ядровых e2e-теста.
>    Удалить модуль «вместе с его тестами» нельзя: пропала бы защита у живого поведения.
> 3. Вывод: чистка идёт **слоями, а не списком модулей**, и сначала решается судьба публичного API (вопрос 1).
> Инструмент исправлен (колонки «dead in production» / «live only through app.main» / «кто держит живым в тестах»),
> тест `test_imported_only_by_main_is_live_not_dead` закрепляет ошибку; мутация (не учитывать импорты `main`) его роняет.
> Базовая линия до любых удалений: unit 1 740 passed (504 skipped без БД) + интеграционные 491 passed.

## Контекст

Репозиторий — артефакт статьи: читатель должен увидеть чистый код прототипа, а не рядом с ним то, что осталось от M1
(LangGraph-графы, approval-слой, аудит tool-calls, путь-права, M1-верификация). [ADR-002](ADR-002.md) выбирал LangGraph как
основной runtime; прототип его **не использует**: свой цикл ~100 строк (`app/sandbox/agent_loop.py`), см. `PROGRESS.md`.
Но M1-код всё ещё в дереве, в зависимостях и в тестах. В `docs/ROADMAP.md` размер считался по каталогам целиком (например, `services/` ≈ 4,9 тыс. строк, но там есть и ядро прототипа); измерение по модулям точнее и ниже: см. цифры ниже.

## Как измерено (и чего это не доказывает)

Статический граф импортов `app.*` (модуль `ast`, поэтому импорты внутри функций учтены), три измерения:
1. **Достижимость** из ядра прототипа (`bootstrap`, нужные API-роутеры, `core`, `db`). `app.main` регистрирует *все* роутеры,
   поэтому его импорты не учитываются, иначе весь M1 API выглядел бы «используемым».
2. **Граница**: импорты из ядра *в* M1. Каждая строка = место, которое надо переделать **до** удаления.
3. **Тесты**: что импортирует каждый тестовый файл.

Что инструмент **не** делает: «M1» здесь — *предложение*, заданное паттерном имён (`M1_RE` в скрипте), а не вывод. Статический
анализ не видит динамических импортов; «достижимо» не значит «нужно». Решение об удалении — человеческое.

## Главные цифры

- **52% `app/` (4 838 из 9 218 строк, 59 модулей) — унаследованный M1.**
- **Мертвы в проде 1 389 строк (15 модулей)**, ещё 784 строки (9 модулей) живы только через `app.main` (API approvals/evidence). Но удалить мёртвое сразу нельзя: его используют тесты (см. поправку).
- Всё M1 в целом связано с ядром **20 импортами** (таблица ниже): это конкретный список мест, а не «вплетено везде».
- Тесты: 108 файлов / 24 153 строки. **18 файлов (4 273 строки) целиком про M1**; 27 (9 214 строк) в основном про M1 (проверить, потом удалить);
  11 (4 308 строк) смешанные (вырезать M1-половину); 44 файла (5 703 строки) остаются без изменений.
  Т.е. удаляется порядка **13 тыс. из 24 тыс. строк тестов**. Это самый рискованный пункт: «зелёный» набор должен остаться осмысленным.
- Неожиданность, ради которой стоило мерить: песочница держит **весь LangGraph-граф** живым ради одной функции классификации
  ошибок OpenAI (`sandbox.runner → agent_runtime.error_classification → agent_graph → fixture_tools`), потому что файл импортирует
  типы исключений графа.

## Предлагаемое решение

**Оставляем:** `domain/` (state machines), `repositories/`, `AgentService.execute_run`, учёт стоимости/usage, публичный API
(`tasks`, `workspaces`, `agent_runs`, `sandbox_runs`, `health`), CLI (`solve/report/patch/run/task/workspace`), `sandbox/`, `bootstrap`.

**Удаляем:** `agent_runtime/` (LangGraph-графы, демо, fixture-инструменты), `tools/` (approved `apply_patch`, registry), `permissions/`,
approval-слой (`approval_*`, `pending_approvals`, `approved_*`, API `approvals`), аудит tool-calls, M1-verification
(`verification_service/observer/contract/evidence`) и API/CLI `evidence`, `approval`.

### Порядок PR (пересмотрен: слоями; оценка 4 PR, 4–6 рабочих дней; прежние «2–3 дня» были занижены)
Принцип: **каждый PR удаляет слой целиком вместе с его тестами и подставками, а перед удалением измеряется покрытие ядра**
(`coverage` по модулям ядра до и после: удаление M1-тестов не должно снижать покрытие того, что остаётся; если снижает —
в PR появляется ядровой тест, не M1-подставка).
1. **C2: подготовительные разрезы без изменения поведения** (разрезы 1–3: классификация ошибок OpenAI, enum `VerificationVerdict`,
   `metadata_digest`). После него песочница и `schemas` не импортируют M1. Защита: существующие тесты. Маленький PR.
2. **C3: удалить слой «approval / evidence / tool-calls / M1-verification» целиком** (API, CLI `approval`/`evidence`, сервисы,
   `tools/`, `permissions/`, схемы и тесты этих слоёв, плюс подставки `approved_*`, `audited_*`, `repository_agent_runner`).
   Ядровые e2e-тесты, которые брали `verification_service`/`repository_agent_runner` как подставку, переводятся на реальный
   путь `SandboxVerifier`. Разрезы 4–7. **Меняет публичный API/CLI** (вопрос 1). Самый крупный PR.
3. **C4: LangGraph из ядра**: тесты `AgentService` переводятся с `LangGraphAgentRunner` + `create_agent_graph` на простой
   тест-дублёр `AgentRunner` (возвращает `AgentFinalResult` или бросает `AgentRunnerError`); удаляются `agent_runtime/` и
   зависимость `langgraph` (проверить, что нужно прототипу от `langchain-*`).
4. **C5: БД и документы**: миграция снимает `tool_calls`, `approvals` (и проверить `artifacts`); README/архитектура без M1.

### База данных
Таблицы M1: `tool_calls`, `approvals` (и `artifacts`: проверить, использует ли её песочница; артефакты прототипа лежат в файловом хранилище).

## Риски
- **Потеря проверок.** 13 тыс. строк тестов M1 защищали и общее: идемпотентность, состояния, отмену. Часть из них — тесты ядра, написанные на M1-фикстурах. Правило C4: удаляем тест только с записью, где теперь защищено то же поведение.
- **Публичный API/CLI меняется** (`approvals`, `evidence`, события `approval_*`/`tool_call_*`). Сейчас пользователь один (владелец), но это надо сказать явно.
- **Статический анализ неполон**: перед удалением каждого модуля — поиск по строкам (`getattr`, динамические импорты, Alembic), CI как арбитр.

### Вопрос 1 по-простому: что изменится
- **Что это такое.** Наследие M1: агент «предлагает патч → человек подтверждает» (human-in-the-loop). В прототипе этого нет: решает
  независимый Verifier (тесты красные до, зелёные после, тесты не тронуты). `forge solve/report/patch/run/task/workspace` этих
  эндпоинтов **не используют**: CLI ходит по HTTP только за тем, что нужно ему.
- **Что исчезнет.** HTTP: 4 маршрута approvals (3 чтения + решение) и 2 маршрута evidence. CLI: `forge approval list|get|review|approve|reject`
  и `forge evidence list|get`. События старых запусков вида `approval_*`/`tool_call_*` в БД станут обычными «прочими».
- **Кого заденет.** Сейчас пользователь один (ты), и демо/evals этого не вызывают. Внешних клиентов API нет.
- **Не теряем идею.** В части D (GitHub PR flow) роль «человек подтверждает» играет сам PR и его ревью: это и есть нативный approval.
- **Что откатывается легко:** всё в git; PR можно не вливать.
