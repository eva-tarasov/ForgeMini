# ForgeMini — дорожная карта после прототипа

Состояние на 2026-11-22: прототип работает (`forge solve`: репозиторий + задача + команда тестов → агент в Docker-sandbox →
независимая проверка → проверенный diff или объяснение отказа). Живые прогоны demo-calc: 3 из 3 решаемых задач
`succeeded`, неразрешимая — честный `cannot_fix`. Подробности — `PROGRESS.md`.

## Как читать оценки
- **Единица — «шаг» = один PR = одна рабочая сессия** (код и тесты пишу я, ты ревьюишь, мёржишь и делаешь живые прогоны
  на своём Mac). Один шаг ≈ полдня–день календарного времени, если ты отвечаешь в тот же день.
- **Календарные сроки — прогноз, не обещание.** Опора — фактический темп: Day 0–3 (песочница, Verifier, bootstrap,
  CLI, живой запуск, тюнинг) уложились в ~2,5 дня при ежедневном участии. Главные источники отклонений: время на твоё
  ревью/живые прогоны и сюрпризы, которые вылезают только при живом запуске (так было: формат ответа API, образ sandbox).
- Всё, что требует **ключей и внешнего мира** (OpenAI, GitHub), проверяется на твоей машине; в моей среде нет доступа к
  этим сервисам, поэтому такие шаги всегда имеют «хвост» — один цикл «ты запустил → прислал вывод → я поправил».

## Рекомендуемый порядок

| # | Этап | Шагов | Календарно* | Зависит от | Зачем именно здесь |
|---|---|---|---|---|---|
| A | **Демо** (свой репозиторий с багами, красивый CLI, клонирование по URL, сценарий показа) | 2 | 1–2 дня | — | Визуальный результат; материал для статьи |
| B1 | **Мини-evals** (5–6 задач × несколько прогонов: доля успехов, шаги, токены, доля честных отказов) | 1–2 | 1–2 дня | A | Недетерминизм уже виден (5 и 6 шагов на одной задаче); читатель-скептик и агент-читатель хотят числа |
| C | **Чистка кода M1** (слоями, ADR-003) | 4 | 4–6 дней | — | Репозиторий — артефакт статьи и будущий публичный: читатель должен увидеть чистый код. *Оценка пересмотрена вверх (было 2–3 дня): тесты используют «мёртвый» код как подставки, удаляется слоями вместе с тестами и с измерением покрытия ядра* |
| F′ | **CLI-демо для менеджеров**: доводка терминального вида, карточка вердикта, сценарий показа, запись; опционально `forge replay` | 1–2 | 1–2 дня | A, B1 | Показ людям без техподготовки через хорошо оформленный CLI (веб-версию **не делаем**: решение владельца) |
| G | **Публикация репозитория**: скан секретов (gitleaks), лицензия **MIT**, README для чужих, **новый репозиторий с переписанной историей** (без личного e-mail) | 1–2 | 1–2 дня | C | Открыть репозиторий можно, когда в нём нет M1 и личных путей |
| B2 | **Статья**: черновик → правки → публикация | 2–3 | 2–3 дня | A, B1; публикация лучше после C | См. `docs/article/PLAN.md` |
| D | **GitHub PR flow** (+ prerequisite: установка зависимостей) | 4 | 3–4 дня | A (URL-источник) | Из «патча в терминале» в продукт: готовый PR с доказательствами |
| E | **Очередь на PostgreSQL + worker** | 3–4 | 3–4 дня | C (меньше кода вокруг) | Надёжность и параллелизм: сейчас run живёт в памяти процесса |

\* при ежедневном участии. Суммарно **≈ 14–21 рабочих дней, т.е. 3–4 недели** (было 12–18 до пересмотра C и добавления F′, G).
Статью можно публиковать после A+B1+C+F+G; D и E дают ей продолжение.

**Последовательность (решение владельца):** A ✅ → B1 ✅ → C ✅ → стоимость рана ✅ → **F′ (CLI-демо)** → **G + B2 (статья)** → D → E.
Прежняя рекомендация «F перед C» держалась на веб-версии; после решения «веб не делаем» она снята. F′ идёт после C: правки
CLI (`approval`/`evidence` удаляются в C3) и вид `SolveView` лучше доводить на уже чистом коде и по твоему живому прогону демо.

**Не в приоритете (по решению владельца):** голосовой ассистент, приложение для Mac / SwiftUI-клиент. Возвращаемся после E.

### Почему чистка (C) идёт раньше D и E
1. **D и E переписывают те же места, где сидит M1.** `AgentService`, `AgentRunner` и `InProcessRunCoordinator` несут ветки
   approvals (разрезы 5 и 6 в ADR-003). Очередь (E) заменяет координатор: без чистки пришлось бы переносить на новый код методы,
   которые потом удаляются.
2. **Налог на каждый следующий шаг.** Сейчас около половины тестов (≈13 из 24 тыс. строк) про M1; любой PR в D/E обязан держать их
   зелёными и ждёт ~3 минуты интеграционного CI. Чистка один раз убирает этот налог.
3. **Публичный репозиторий и статья.** Читатель видит код, под которым лежит чужое прошлое; в цитатах кода для статьи будут
   LangGraph-графы, которых прототип не использует.
Против: C даёт 4–6 дней без видимого продукта. Поэтому F стоит перед ней. Если захочешь видимого результата ещё раньше,
D можно делать до C: цена — перенос M1-веток в D, см. п. 1.

### Почему не ровно в твоём порядке (чистка → очередь → GitHub)
Предлагаю **GitHub PR flow раньше очереди**: он даёт видимую продуктовую ценность и требует «setup-фазы» зависимостей —
без неё ForgeMini работает только на репозиториях без зависимостей (в sandbox нет сети; демо-библиотеки на `unittest`
этого пока не замечают, любой реальный проект замечает). Очередь — инженерная надёжность; её польза не видна, пока не
появится параллельная нагрузка. Но порядок D/E взаимозаменяем — решение за тобой.

## A. Демо
1. Демо-репозиторий `forge-demo-shop`: реалистичная мини-библиотека с историей коммитов и тремя багами разной природы.
2. `forge solve --repo <git URL>` (клонирование, безопасное), структурированные шаги агента, красивый вывод в терминале
   (только в TTY; plain и `--json` не меняются), сценарий `demo/run.sh` по сценам.
3. После твоего живого прогона — правки по увиденному и запись (asciinema / GIF).

## B1. Мини-evals
Набор задач (решаемые разной сложности, неразрешимая, «провокация» — соблазн править тест), прогон N раз, таблица:
доля `succeeded`, доля честных `cannot_fix`, ложные успехи (должно быть 0 — это главная метрика), медиана шагов/токенов.
Запускается тобой (твой ключ; объём небольшой и явный). Результат — таблица в `PROGRESS.md` и в статью.

## C. Чистка M1 (ADR-003)
Размеры (измерено `scripts/inventory/import_graph.py`): `app/` — 9,2 тыс. строк, из них 52% (4,8 тыс.) унаследованный M1; тесты —
24 тыс. строк, около 13 тыс. про M1. Оставляем: domain/state machines, репозитории, `AgentService.execute_run`, учёт стоимости,
публичный API задач и запусков, CLI (`solve/report/patch/run/task/workspace`), sandbox. Решения владельца: удалить публичные
`approval`/`evidence` (подтверждено), снять таблицы миграцией, удалить `docs/archive/`.
1. **C1 ✅ инвентаризация + ADR-003** (PR #9, дополнен поправкой: «мёртвый в проде» ≠ «можно удалить», тесты держат подставки).
2. **C2 ✅ подготовительные разрезы** (PR #13) без изменения поведения: классификация ошибок OpenAI, enum вердикта, `metadata_digest`.
3. **C3 ✅ слой «approval / evidence / tool-calls / M1-verification»** (PR #14) целиком вместе с тестами и подставками; ядровые e2e на
   `SandboxVerifier`; **покрытие ядра до и после**.
4. **C4 ✅ LangGraph из ядра** (PR #15): тесты `AgentService` на простом дублёре runner, удаление `agent_runtime/` и зависимости `langgraph`.
5. **C5 ✅ БД и документы** (PR #16): миграция `c5a1f0d2e7b9` (снимает `tool_calls`/`approvals`/`artifacts` и `waiting_approval`), ADR-002 помечен заменённым, итог в ADR-003.

**Итог C:** `app/` 9,2 → ≈4,1 тыс. строк, M1 — 0; покрытие ядра не упало ни на одном шаге (цифры — ADR-003, «Итог»).
**Сделано следом (решение владельца, PR #17):** цикл песочницы подключён к ядровому `UsageCollector`; тариф из `.env` (`FORGE_PRICE_*`); стоимость рана в `/result` и `forge report`.
Риск: удаление половины тестов — «зелёный» набор должен остаться осмысленным: каждое удаление сопровождается строкой
«что защищал / где защищено теперь», и покрытие ядра не падает.

## F′. CLI-демо для менеджеров
Решение владельца: **веб-интерфейс не делаем**; хорошо оформленного CLI достаточно. Цель: человек без техподготовки за 2–3 минуты
понимает, **что сделал агент и почему этому можно верить**. Вход: твой живой прогон `scripts/demo/run.sh` (вывод/скриншот).
1. **Вид** (часть сделана по живому прогону, PR #18: короткие пути, сводка тестов, «tests fail/pass», стоимость в рамке): отступы, группировка, понятные подписи шагов человеческим языком, цвета по смыслу (зелёный только у независимо
   проверенного результата).
2. **Карточка вердикта** ✅ (PR #19: числа тестов «до/после», стоимость; вторая история `--story refuse`, шпаргалка `--cues`) в конце: «Проверено независимо» / «Не удалось, и вот почему» / «Не проверено» + доказательство
   в двух строках (до: N тестов падает; после: все проходят; тесты не тронуты) + стоимость.
3. **Сценарий показа** (`scripts/demo/run.sh`): реплики-подводки для ведущего, паузы, один синтетический сценарий на `demo-shop`.
4. Запись (asciinema/GIF) делает владелец. Опционально: `forge replay <файл>`: проигрывание записанного прогона без ключа и сети
   с пометкой «запись» (вычёркивается, если не нужно).

## G. Публикация репозитория
**Сделано (шаг 16):** история переписана и опубликована в публичном `eva-tarasov/ForgeMini`, `ForgeMini-dev` — приватный архив, тег не ставим. Осталось: выгрузка описаний PR в `docs/history/`, GIF, публикация статьи.

Скан секретов и личных данных по всей истории (не только по текущему дереву), удаление личных путей (`/Users/...`),
лицензия **MIT** (владелец выбрал), README для чужих людей. **История git**: личный e-mail автора есть в метаданных 6 коммитов
(автор и коммитер), в файлах его нет; плюс имя macOS-пользователя в путях `/Users/...` старых файлов. Решение владельца: убрать.
`git filter-repo` (mailmap + замена текста) меняет все хеши и тег `forge-m1-baseline`. **Подвох:** GitHub хранит
`refs/pull/N/head` (сейчас 11), force-push их не перепишет, и старые коммиты остались бы доступны по хешу в публичном
репозитории. Поэтому: **новый репозиторий** с переписанной историей, старый удалить или оставить приватным; описания PR
(материал «почему» для статьи) выгружаем в `docs/history/`. Force-push, тег и создание репозитория делает владелец по скрипту
(из сессии они заблокированы); делается в самом конце: перепись посреди работы ломает все ветки. В статье раскрываем роль AI и
названия моделей.

## D. GitHub PR flow
0. **Установка зависимостей (setup-фаза)**: отдельная фаза с сетью, до песочницы без сети (производный образ или
   volume с зависимостями). Это исполнение кода из репозитория с сетью → opt-in и явная команда (`--setup "pip install -r
   requirements.txt"`), риски описываем в ADR.
1. **Доступ к GitHub**: fine-grained токен только в локальном `.env` (никогда в чате), чтение приватных репозиториев.
2. **PR**: ветка → коммит → push → открытие PR; в описании — вердикт Verifier, тесты до/после, расход токенов.
3. **Из issue**: `forge solve --issue <URL>` — текст issue становится целью; отчёт комментарием в issue/PR.
Риск: живая проверка только у тебя (нужен тестовый репозиторий и токен).

## E. Очередь на PostgreSQL + worker
Сейчас run исполняется в памяти процесса API (`InProcessRunCoordinator`): перезапуск сервера теряет run, параллелизм не
управляется.
1. Таблица заданий + постановка в очередь + захват через `SELECT … FOR UPDATE SKIP LOCKED`.
2. Процесс-worker: аренда (lease) и heartbeat, тайм-аут «зависшего» задания, ограниченные повторы, корректная остановка, отмена.
3. API/CLI: `start` ставит в очередь; лимит параллельных контейнеров и ресурсов.
4. **Хаос-тесты**: `kill -9` worker посреди run → run детерминированно восстановлен или помечен failed; идемпотентность.
Хороший материал и для статьи, и для system design-вопросов (at-least-once, идемпотентность, lease vs lock).

## Что может сдвинуть сроки
- Живые прогоны выявят новые находки (как формат `content` у Responses API) — закладываю «хвост» на каждый этап с живой моделью.
- Чистка M1 может вскрыть неявные зависимости (например, M1-таблицы, на которые опирается публичный API).
- Для D нужен тестовый GitHub-репозиторий и токен у тебя.
- Если статью решим публиковать вместе с открытием репозитория — нужна проверка истории git на секреты и пути (см. `docs/article/PLAN.md`).
