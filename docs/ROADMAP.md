# ForgeMini — дорожная карта после прототипа

Состояние на 2026-11-22: прототип работает (`forge solve`: репозиторий + задача + команда тестов → агент в Docker-sandbox →
независимая проверка → проверенный diff или объяснение отказа). Живые прогоны demo-calc: 3 из 3 решаемых задач
`succeeded`, неразрешимая — честный `cannot_fix`. Подробности — `PROGRESS.md`.

## Как читать оценки
- **Единица — «шаг» = один PR = одна рабочая сессия** (код и тесты пишу я, ты ревьюишь, мёржишь и делаешь живые прогоны
  на своём Mac). Один шаг ≈ полдня–день календарного времени, если ты отвечаешь в тот же день.
- **Календарные сроки — прогноз, не обещание.** Опора — фактический темп: Day 0–3 (песочница, Verifier, bootstrap,
  CLI, живой запуск, тюнинг) уложились в ~2,5 дня при ежедневном участии. Главные источники отклонений: время на твоё
  ревью/живые прогоны и сюрпризы, которые вылезают только при живом запуске (так было: формат ответа API, образ sandbox).
- Всё, что требует **ключей и внешнего мира** (OpenAI, GitHub), проверяется на твоей машине; в моей среде нет доступа к
  этим сервисам, поэтому такие шаги всегда имеют «хвост» — один цикл «ты запустил → прислал вывод → я поправил».

## Рекомендуемый порядок

| # | Этап | Шагов | Календарно* | Зависит от | Зачем именно здесь |
|---|---|---|---|---|---|
| A | **Демо** (свой репозиторий с багами, красивый CLI, клонирование по URL, сценарий показа) | 2 | 1–2 дня | — | Визуальный результат; материал для статьи |
| B1 | **Мини-evals** (5–6 задач × несколько прогонов: доля успехов, шаги, токены, доля честных отказов) | 1–2 | 1–2 дня | A | Недетерминизм уже виден (5 и 6 шагов на одной задаче); читатель-скептик и агент-читатель хотят числа |
| C | **Чистка кода M1** | 3–4 | 2–3 дня | — | Репозиторий — артефакт статьи: читатель должен увидеть чистый код, а не 7,5 тыс. строк унаследованного |
| B2 | **Статья**: черновик → правки → публикация | 2–3 | 2–3 дня | A, B1; публикация лучше после C | См. `docs/article/PLAN.md` |
| D | **GitHub PR flow** (+ prerequisite: установка зависимостей) | 4 | 3–4 дня | A (URL-источник) | Из «патча в терминале» в продукт: готовый PR с доказательствами |
| E | **Очередь на PostgreSQL + worker** | 3–4 | 3–4 дня | C (меньше кода вокруг) | Надёжность и параллелизм: сейчас run живёт в памяти процесса |

\* при ежедневном участии. Суммарно **≈ 12–18 рабочих дней, т.е. 3–4 недели**; статью можно публиковать уже после
A+B1+C (≈ через 1–1,5 недели) — дальше она получает продолжение.

**Не в приоритете (по решению владельца):** голосовой ассистент, приложение для Mac / SwiftUI-клиент. Возвращаемся после E.

### Почему не ровно в твоём порядке (чистка → очередь → GitHub)
Предлагаю **GitHub PR flow раньше очереди**: он даёт видимую продуктовую ценность и требует «setup-фазы» зависимостей —
без неё ForgeMini работает только на репозиториях без зависимостей (в sandbox нет сети; демо-библиотеки на `unittest`
этого пока не замечают, любой реальный проект замечает). Очередь — инженерная надёжность; её польза не видна, пока не
появится параллельная нагрузка. Но порядок D/E взаимозаменяем — решение за тобой.

## A. Демо
1. Демо-репозиторий `forge-demo-shop`: реалистичная мини-библиотека с историей коммитов и тремя багами разной природы.
2. `forge solve --repo <git URL>` (клонирование, безопасное), структурированные шаги агента, красивый вывод в терминале
   (только в TTY; plain и `--json` не меняются), сценарий `demo/run.sh` по сценам.
3. После твоего живого прогона — правки по увиденному и запись (asciinema / GIF).

## B1. Мини-evals
Набор задач (решаемые разной сложности, неразрешимая, «провокация» — соблазн править тест), прогон N раз, таблица:
доля `succeeded`, доля честных `cannot_fix`, ложные успехи (должно быть 0 — это главная метрика), медиана шагов/токенов.
Запускается тобой (твой ключ; объём небольшой и явный). Результат — таблица в `PROGRESS.md` и в статью.

## C. Чистка M1 (ADR-003)
Размеры (измерено): backend — 10,9 тыс. строк, из них M1-специфичны `services/` (≈4,9 тыс.: approvals, аудит tool-calls,
M1-verification), `tools/` (1,4 тыс.), `agent_runtime/` (1,1 тыс., LangGraph), `permissions/`; тесты — 28 тыс. строк, 57 из
104 файлов связаны с M1. Оставляем: domain/state machines, репозитории, `AgentService.execute_run`, учёт стоимости,
публичный API, CLI, sandbox.
1. **Инвентаризация + ADR-003**: карта зависимостей (что импортирует что), решение по каждой подсистеме и по таблицам БД
   (удалять миграцией или оставить схему?), список удаляемых CLI-команд (`approval`, `evidence`).
2. **Удаление**: LangGraph-графы, fixture-инструменты, approved `apply_patch`, path-permissions, approval-слой вместе с
   тестами; поддерживаем зелёный CI на каждом коммите.
3. **БД и унификация**: миграция (если решили чистить схему), слияние M1-verification и `SandboxVerifier` в один путь.
4. **Документы**: README/архитектура, удаление ссылок на M1.
Риск: удаление половины тестов — «зелёный» набор должен остаться осмысленным (не терять проверки того, что остаётся).

## D. GitHub PR flow
0. **Установка зависимостей (setup-фаза)**: отдельная фаза с сетью, до песочницы без сети (производный образ или
   volume с зависимостями). Это исполнение кода из репозитория с сетью → opt-in и явная команда (`--setup "pip install -r
   requirements.txt"`), риски описываем в ADR.
1. **Доступ к GitHub**: fine-grained токен только в локальном `.env` (никогда в чате), чтение приватных репозиториев.
2. **PR**: ветка → коммит → push → открытие PR; в описании — вердикт Verifier, тесты до/после, расход токенов.
3. **Из issue**: `forge solve --issue <URL>` — текст issue становится целью; отчёт комментарием в issue/PR.
Риск: живая проверка только у тебя (нужен тестовый репозиторий и токен).

## E. Очередь на PostgreSQL + worker
Сейчас run исполняется в памяти процесса API (`InProcessRunCoordinator`): перезапуск сервера теряет run, параллелизм не
управляется.
1. Таблица заданий + постановка в очередь + захват через `SELECT … FOR UPDATE SKIP LOCKED`.
2. Процесс-worker: аренда (lease) и heartbeat, тайм-аут «зависшего» задания, ограниченные повторы, корректная остановка, отмена.
3. API/CLI: `start` ставит в очередь; лимит параллельных контейнеров и ресурсов.
4. **Хаос-тесты**: `kill -9` worker посреди run → run детерминированно восстановлен или помечен failed; идемпотентность.
Хороший материал и для статьи, и для system design-вопросов (at-least-once, идемпотентность, lease vs lock).

## Что может сдвинуть сроки
- Живые прогоны выявят новые находки (как формат `content` у Responses API) — закладываю «хвост» на каждый этап с живой моделью.
- Чистка M1 может вскрыть неявные зависимости (например, M1-таблицы, на которые опирается публичный API).
- Для D нужен тестовый GitHub-репозиторий и токен у тебя.
- Если статью решим публиковать вместе с открытием репозитория — нужна проверка истории git на секреты и пути (см. `docs/article/PLAN.md`).
