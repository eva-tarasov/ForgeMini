# ForgeMini — прогресс

Формат: коротко. Подробности и «почему» — в описаниях PR. Старая история M1 — в git, коммит `e5d6377` (`git show e5d6377:forge_progress.md`, учебные гайды — `git show e5d6377:docs/LEARNING_GUIDE.md`). PR #1–#20 — в приватном архиве ForgeMini-dev (см. шаг 16).

## Цель прототипа (v0.1-prototype, ~3 дня)
`forge solve --repo <path> --goal "<что исправить>" --test "<команда тестов>"` (не `forge run`: группа `run` уже занята create/start/watch) →
агент чинит код в Docker-sandbox (без сети) → Verifier в чистом контейнере прогоняет тесты →
`succeeded` + проверенный diff, либо `failed` + понятное объяснение.

## Решения
- **Sandbox через Docker CLI, не SDK**: на одну зависимость меньше, одинаково на Linux/macOS. Код копируется в контейнер (`tar`), а не монтируется: агент физически не может писать в ваш checkout.
- **Changeset вместо `git diff` в контейнере**: в `python:3.12-slim` нет ни `git`, ни `patch`. Единица истины — content-addressed changeset (sha256); diff для человека строится из него. Verifier применит *тот же* changeset к чистому исходнику.
- **Ошибка инструмента возвращается модели** (`ToolMessage(status="error")`), а не роняет run. В M1 было наоборот — отсюда 4 «UNKNOWN» в live-smoke.
- **Свой цикл ~100 строк вместо LangGraph**: нужные нам гарантии (бюджет шагов, видимость ошибок) явно читаются в одном файле.
- `succeeded` не выставляется нигде в этом слое: runner отдаёт `ready_for_verification` / `blocked`.
- Тесты интеграции: вместо правки ~24 файлов с 5 разными guard-паттернами имён БД — скрипт `scripts/ci/integration_tests.sh`
  создаёт БД под каждый паттерн. Дёшево и без риска сломать тесты; единый флаг — позже, при чистке.

- **Verifier (Day 2) — правила вердикта.** PASS только если: (1) тесты красные на нетронутом исходнике (baseline), (2) зелёные с changeset в *свежем* контейнере, (3) не изменены/удалены тестовые файлы, (4) changeset не пуст. Baseline уже зелёный → INCONCLUSIVE (нечего чинить); падение инфраструктуры → INCONCLUSIVE, не FAIL. `succeeded` ставит только Verifier.
- **Run-конфигурация живёт в Workspace** (`source_path`, `test_command`, `image`), а не в Task: один репозиторий — много задач. `bootstrap.py` — composition root: в M1 `app = create_app()` не имел привязки исполнения (503).
- **Шаги агента — публичные события `agent_step`** (сжатые head+tail), чтобы `forge solve` мог показывать прогресс; старый строгий read-API расширен, а не обойдён.
- **Контракт CLI не ломаем**: новые поля workspace (`source_path/test_command/image`) не сериализуются, когда `null` — JSON настроенного/ненастроенного workspace совместим с прежним (тесты `cli03 bytes`).
- INCONCLUSIVE пока отображается как run `failed` (отдельного статуса нет) — причина видна в `forge report`.

## Находки по ходу (для статьи)
- **Модель не знала, какие утилиты есть в песочнице** → в 3 из 4 прогонов вызов `rg` (exit 127) впустую. Лечение — честный блок «Environment» в системном промпте (что есть / чего нет). Чтобы промпт не врал, есть тест, который проверяет в реальном контейнере: обещанные утилиты существуют, «отсутствующие» — нет (вторая половина — только на стандартном `python:3.12-slim`, т.е. в CI).
- **Мой локальный образ sandbox был богаче боевого** (`forge-sandbox:local` с `rg`, `git`, `patch`, `curl`, `make`, т.к. из облака нельзя тянуть Docker Hub). Всё локальное тестирование шло на другом окружении, чем у владельца; арбитром образа является CI. Урок: «у меня зелёное» ничего не значит, если окружение отличается — выпишите различия.
- **`has_patch` было истинно для запуска без правок** (проверялось существование артефактов, а не непустоту диффа): отчёт предлагал `forge patch` для честного `cannot_fix`. Теперь `has_patch` = непустой дифф; `/patch` отвечает 404 «агент ничего не менял». Мутационно подтверждено.
- **Расход ресурсов виден в отчёте** (`usage`: вызовы модели, вызовы инструментов, токены). Денежную оценку не считаем: цены зависят от модели и меняются. Если провайдер токены не сообщил — так и пишем, а не «0».
- **Живая модель показала то, чего не видела фейковая.** API Responses отдаёт `content` списком блоков (`reasoning` с зашифрованным payload, `function_call`, текст), а цикл делал `str(content)`: в прогресс-поток, события в БД и `transcript.json` попадал repr сырых объектов API. Сценарная модель всегда возвращала строку, поэтому все тесты были зелёными. Лечение: `message_text()` берёт только текстовые блоки; тест воспроизводит точную форму из живого вывода, мутация (возврат к `str()`) его валит. Урок: фейк повторяет ваши предположения о формате, а не реальность — первый живой прогон надо смотреть глазами.
- Мой первый тест на «нет сети» был бы зелёным и без изоляции: в облачной среде интернета нет вообще. Заменён на проверку «в контейнере только интерфейс `lo`»; проверено, что без `--network none` появляется `eth0`.
- Мутационная проверка ключевого теста (модель видит ошибки инструментов): сломал код — тест упал, вернул — зелёный.
- **Verifier проверен мутацией.** Первый «сценарий читера» (правка теста, который и так не мог пройти) был слабым. Заменён настоящей атакой — ослабить ожидание в `tests/test_average.py`; с выключенной защитой protected-файлов она даёт ложный PASS, с включённой — FAIL. Тест реально охраняет правило.
- **Первый запуск у владельца не сработал — инструкция была неполной.** В «Запуске» не было шага установки зависимостей (он был только в «Разработке»); `uvicorn` взялся из глобального Python, `langchain_core` не нашёлся. Лечение: `scripts/start.sh` с предпроверками (каждая проблема — одна понятная причина), запуск через `python -m uvicorn/alembic`, таблица «Если что-то не работает» в README. Урок для статьи: инструкция «как запустить» — такой же код, её надо исполнять с нуля, в чистом окружении.
- **Вторая итерация: инструкция всё ещё требовала ручной правки `.env`, и владелец застрял** (плюс `command not found: python/forge` — на macOS нет `python`, а в новом терминале не активирован venv). Лечение: `scripts/setup.sh` (генерирует пароль, спрашивает ключ скрытым вводом, сам предлагает сбросить старый том БД), README в виде таблицы «два терминала», `forge solve` проверяет доступность сервера до создания чего-либо, подсказки в отчёте зависят от кода сбоя (ключ/сеть/модель/Docker вместо «уточните задачу»). Проверено прогоном с нуля в чистой копии (новый venv → setup → start → solve с фальшивым ключом → понятное `provider_connection`).
- **Баг в моём же стартовом скрипте, найденный тестом в «грязном» окружении:** `POSTGRES_HOST="$(...)"` перезаписывал уже экспортированную переменную пустой строкой → pydantic отверг. Скрипт теперь только читает значения в локальные переменные; приоритет «окружение главнее .env» — как у `Settings`. Зафиксировано тестами `test_bootstrap_settings.py`.
- `FORGE_SANDBOX_IMAGE` из `.env` молча игнорировался (`default_image()` читал только `os.environ`) — теперь bootstrap применяет значение из `.env`.
- **«Зелёный» прогон CLI проверял старый код.** Editable-установка в venv указывала на каталог `myfirstforge/`, а не на `forgemini/`: 754 passed относились к старой копии. Поймано, только когда импорт нового модуля упал. Урок: после смены каталога — `python -c "import pkg; print(pkg.__file__)"`; backend-тесты были верны, т.к. запускались из `backend/` (cwd первый в `sys.path`), но установка тоже перенацелена.
- Превью результата в transcript сначала резало хвост, а вердикт unittest (`FAILED`/`OK`) в конце — тест это поймал; теперь head+tail.

## Демо (шаг 4)
- **Цель**: показать глазами цепочку «чужой репозиторий → баг → задача → исправление → независимая проверка». Репозиторий `examples/forge-demo-shop` (библиотека цен `shopkit`, только stdlib) написан под демо: 3 независимых бага (`>` вместо `>=` на пороге бесплатной доставки; банковское округление в `round()` вместо коммерческого; купоны суммируются вместо «лучшего одного»), правила — в `docs/pricing-rules.md`, красные регрессионные тесты — в последнем коммите истории из 6 коммитов (`scripts/demo/make_demo_repo.sh`).
- **Тест, который ничего не проверял, поймали на самом себе**: первый регрессионный тест на округление проходил и с багом (0.075 при банковском округлении тоже даёт 0.08). Заменён случаем 0.045; тест `test_the_vat_regression_test_is_not_weak` проверяет, что каждый случай *падает* с багом.
- **Структурные поля шагов** (`turn/tool/target/ok/exit_code/outcome`) рядом с текстовым `summary`: клиенту не нужно разбирать прозу, чтобы нарисовать таймлайн. В `target` только команда или путь (≤200 символов), содержимое файлов в событие не попадает (тест).
- **`--repo` принимает git URL.** URL — недоверенный ввод (его могут скопировать из issue или получить от агента): отклоняются `-…` (git воспримет как опцию, `--upload-pack=<cmd>` исполняет команду), креды в URL (оседают в истории шелла и `.git/config`), `http://`, `ext::` и прочие транспорты; git вызывается с `--`, `GIT_TERMINAL_PROMPT=0`, `GIT_ALLOW_PROTOCOL`. Каждое правило проверено мутацией (удалил проверку — тест упал).
- **`--apply`**: применяется только проверенный патч, `git apply --check` затем `git apply` (всё-или-ничего), отказ при `.git/`, `..`, симлинках и субмодулях в диффе (дифф произвёл агент в песочнице — недоверенный).
- **Живой терминальный вид** (только TTY; pipe, `--json`, CI — прежний текст). Всё от сервера выводится как `Text`, не как rich-разметка: `[red]` в имени файла не перекрасит экран, управляющие символы вырезаются.
- **Что поймал настоящий терминал, а не юнит-тесты**: (1) заголовок «agent at work» не печатался — метод был, вызова не было; (2) строки id слипались в один абзац; (3) подпись в таблице проверки переносилась на вторую строку; (4) в rich-режиме не было подсказки «что делать» при сбое провайдера; (5) дубль «finish». Тест под псевдотерминалом (`pty`) гоняет настоящую команду `forge` против настоящего сервера. Урок тот же, что с live-прогоном: вывод для человека надо читать глазами.
- Скрипт `scripts/demo/run.sh` репетируется подставным `forge` (тест без сервера и LLM), включая «не починил» (код 1, ничего не применено) и «сервер не запущен».

### Стоимость рана (шаг 12, решение владельца «(а)»)
- **Что было:** цикл песочницы считал токены только для отчёта, ядровой учёт (`agent_usage_recorded`, оценка стоимости) пустовал — `usage` в `/result` всегда `null` (находка C4). - **Красный `exit 1` на первом прогоне тестов агентом** читался как «агент ошибся», хотя воспроизвести баг — правильный первый шаг. Если exit code шага — это exit code тестовой команды задачи (команда равна ей или заканчивается ею после `;`/`&&`), CLI пишет «tests fail (exit 1)» / «tests pass». Для `… || true` и пайпов — нет: там exit code уже не вердикт тестов, и подпись была бы ложью.
- **Нет строки стоимости.** Молчание — плохо: ведущий не поймёт почему. Рамка VERIFIED теперь показывает `≈ $…` или «cost not configured»; при отсутствии записи usage (старый сервер/ран) — ничего.
- **Над сценой оставался чужой вывод** — экран очищается перед первой сценой (кроме `--fast`).
- **Проверка:** ruff; unit 687; integration-скрипт зелёный; CLI 548 (+13); evals 46; репетиция `run.sh` с подставным `forge` (7 тестов) и ручной просмотр вывода.
- **Что не проверено здесь:** вид на живой модели и в реальном терминале — это твой следующий прогон.

### F′, часть 2: вердикт в тестах, вторая история, шпаргалка (шаг 14)
- **Карточка вердикта в числах:** «2 of 2 failed (exit 1)» → «all 2 passed (exit 0)» вместо голых кодов. Числа — только из *собственной итоговой строки раннера* (unittest `Ran N tests` / `FAILED (failures=…, errors=…)`, pytest `== 2 failed, 3 passed in … ==`); незнакомый формат → остаётся код выхода. Угаданное число хуже, чем никакого.
- **Вторая история `--story refuse`:** маркетинг просит «бесплатная доставка от 40.00», а `docs/pricing-rules.md` и новый тест «49.99 платит доставку» говорят «от 50.00». Развилка: делать «невыполнимую» задачу с подставным агентом (надёжно, но нечестно) или с живой моделью (честно, но исход непредсказуем). Выбрал задачу, где **честный исход не зависит от модели**: тесты до правки зелёные → Verifier не может сказать PASS *никогда* (сдвиг порога ломает тест, правка тестов запрещена, бездействие — inconclusive). Скрипт считает «не проверено» правильным ответом (код 0), а «проверено» — тревогой (код 1).
- **Тест, который едва не соврал:** проверка предпосылки («порог 40 ломает тест») *прошла бы* — патч не подхватился. Python проверяет свежесть `.pyc` по mtime исходника с точностью до секунды и по размеру; замена `50.00`→`40.00` не меняет размер и случилась в ту же секунду → взят старый байткод. Тест теперь с `python -B`. Проверил, что Verifier этим не страдает: снимок репозитория для контейнера пропускает `__pycache__`/`*.pyc` (уже закреплено `test_from_directory_skips_git_pycache_and_symlinks`).
- **Шпаргалка ведущего — `--cues`, а не режим «реплики во время показа»:** я сначала предлагал второе, но проектор/шаринг экрана показал бы реплики всем. Шпаргалка печатается до показа (второй экран/телефон), по-русски.
- **Мелочи:** pytest собрал мои функции `test_counts`/`tests_line` как тесты (имя на `test`) — переименованы в `count_tests`/`describe_test_run`; команда `forge solve` в сцене 3 печатается по опции на строку (больше не рвётся посреди слова); README — две истории и запись GIF (asciinema + agg).
- **Проверка:** ruff; unit 693; integration-скрипт зелёный; CLI 561 (+13); evals 46; репетиция `run.sh` (13 тестов) + просмотр вывода обеих историй; мутанты: «refuse считает отказ провалом», «errors= не считаются» — убиты.
- **Не проверено мной:** обе истории на живой модели — твой прогон. Особенно интересно, что сделает модель в `refuse`: откажется сама (лучший исход для статьи) или сдвинет порог и будет поймана Verifier.

### G, часть 1: лицензия, статья, решение по истории (шаг 15)
- **MIT** — файл `LICENSE` в корне (правообладатель — владелец, 2026) и раздел в README. Метаданные пакетов не трогал: строковая форма `license = "MIT"` (PEP 639) требует setuptools ≥ 77, а `pyproject` разрешают 61/64; табличная форма устарела; `license-files` не может ссылаться выше папки пакета. Корневой `LICENSE` покрывает весь репозиторий.
- **CLI:** «Why it stopped» больше не повторяет «Agent says» — сервер хранит `agent_cannot_fix: <слова агента>` (API не меняется), на экране остаётся код + «причины выше». 6 тестов.
- **Статья:** черновик целиком написан в Doc (комментарии к абзацам) по фактам из истории git и этого файла; модели и роли раскрыты. Поправка к моему же сообщению владельцу: gate-документов в M1 было **6**, не 13.
- **История git, факты:** личный gmail — в 6 коммитах M1 (автор и коммиттер); путь `/Users/<имя>` — в истории 9 коммитов, в текущем дереве его нет. По документации GitHub перепись на месте + force-push не убирает данные: старые коммиты остаются доступны через PR (`refs/pull/*` — только для чтения) и кэш по SHA, а саппорт помогает лишь с чувствительными данными. Решение — за владельцем (варианты в чате).

### G, часть 2: публичный репозиторий и прогон «глазами постороннего» (шаг 16)

- **Почему новый репозиторий, а не force-push:** GitHub хранит `refs/pull/*` (только чтение), и старые коммиты с e-mail остались бы доступны по хешу.

Две находки:
  1. **Ложный успех в демо.** Без ключа `forge solve` честно выходит с кодом 4 («сервер не может стартовать ран»), но `run.sh --story refuse` считал любой ненулевой код «правильным отказом» и завершался с 0 — «As it should be». Теперь результатом считаются только 0 и 1; иначе демо останавливается со своим кодом и словами «setup problem, not a result». Тест на обе истории; на старом скрипте он красный.
  2. **`start.sh` прятал причину.** Если образ `postgres:17` не скачивается (нет интернета/Docker Hub), скрипт глушил вывод compose и говорил «PostgreSQL did not become healthy» с подсказкой `docker compose logs` — а логов нет, контейнер не создан. Теперь показывает хвост ошибки и называет причину. 2 теста с поддельным `docker`; на старом скрипте тест на скачивание красный.
